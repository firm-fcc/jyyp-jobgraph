# AlgorithmDesign

## 0. 设计概要

基于"岗位-任务-技能"三元分析框架（Wang et al., 2023; 王然等, 2025），将招聘 JD、ArXiv 论文、行业新闻三类异构数据，经过四层流水线转化为可动态更新的岗位能力图谱。

```
数据采集 → 实体抽取 → 能力模型构建 → 动态更新
   ↑                                    │
   └──── 时滞/噪声/抄袭处理（贯穿全流程）────┘
```

### 三元体系核心思想

传统 `Position → Skill` 二元模型跳过了一个关键桥梁——**任务（Task）**。技术变革首先改变的是具体工作任务（"传统内容分发"→"算法推荐与个性化分发"），然后才传导到技能需求。三元模型 `Position → Task → Skill` 捕捉了这个因果链。

图谱本质上是一个**三层概率网络**：节点（Position, Task, Skill）之间以不同强度的边连接，边的强度来自多文档共现积累。岗位-任务-技能的"三元关系"不是存储原语，而是图谱上的路径查询结果——查询从 Position 出发、经 Task 到达 Skill 的两跳路径。

### 数据源

| 数据源 | 时间位置 | 信号特征 |
|--------|----------|----------|
| ArXiv 论文 | 领先 JD 1-3 年 | 技术萌芽信号，学术语言 |
| 行业新闻 | 领先 JD 6-18 个月 | 产业采纳信号 |
| 招聘 JD | 反映当前（滞后 3-12 月） | 最直接的岗位需求证据 |

## 1. 数据采集层

### 1.1 提取目标：节点 + 直接边

每侧数据源处理后产出的是**节点候选**和**双节点间直接边证据**，而非预组装的四字段元组。

各侧能提供的证据类型不同：

| 侧 | 典型可提取节点 | 典型可提取的直接边 | 遗漏字段 |
|----|--------------|-------------------|---------|
| JD侧 | P, T, S 三类 | `P-[职责描述]→T`（岗位职责段落）、`T-[显式关联]→S`（原文明确说"用X做Y"，见 §2.1） | — |
| 论文侧 | T, S（P 可提取但不强求） | `T-[共现]→S` | P 常缺失 |
| 新闻侧 | 视原文密度而定 | `T-[共现]→S`，偶有 `P-[提及]→T` | 信号最稀薄 |
| 简历侧 | P, T, S | `P-[目标]→T`, `T-[掌握]→S` | 无时间戳 |

### 1.2 新闻侧的双通道处理

新闻密度差异大，一条新闻可能详细描述某岗位的技能需求（可提取完整 P, T, S），也可能仅提及一个新技术名词。采用双通道解耦：

| 通道 | 门槛 | 去向 | 用途 |
|------|------|------|------|
| **图谱构建通道** | 至少含 {P, T, S} 之二 | 实体抽取 → 交叉验证 → 边入库 | 驱动图谱结构更新 |
| **信号追踪通道** | 至少含 1 项（无边） | 实体强度时间序列记录 | 驱动前瞻预警灵敏度，不参与图谱构建 |

两通道独立调参，互不掣肘。一条仅提及"AI Agent 开发"的新闻不产生图谱边，但为该任务类别的实体强度时间序列贡献一个数据点。

### 1.3 岗位粒度对齐

论文/新闻中的岗位称谓通常比 JD 侧粗（"AI 工程师" vs "NLP 算法工程师"）。可引入岗位层级关系（从 JD 数据自底向上构建），使粗粒度信号沿层级向下传播到子岗位。

## 2. 实体抽取层

实体抽取层包含两阶段：**图谱感知提取**（LLM 主调用，产出节点 + 直接边证据）和**消歧与归一化**（检索 + 按需 LLM）。上下文信息贯穿整个流程。

### 2.1 图谱感知提取（LLM 主调用）

**输入准备：** 先将当前文本做 embedding，在图中检索 Top-K（≤30）最相关的已有节点术语作为上下文。

**提取逻辑：** LLM 从原始文本中平行提取三类节点和两类直接边证据。不强制推断原本没有的关联：

```json
{
  "timestamp": "2026-06-15",
  "source_type": "jd",
  "nodes": {
    "positions": ["AI应用开发工程师"],
    "tasks": [
      {"raw": "大模型应用开发与集成", "canonical": "大模型应用开发", "match": "semantic_match",
       "context": "负责大模型API的集成与调优工作..."},
      {"raw": "智能体系统开发", "canonical": null, "match": "new_candidate",
       "context": "负责LangChain等Agent框架的编排开发..."}
    ],
    "skills": [
      {"raw": "精通Python编程", "canonical": "编程能力", "match": "semantic_match",
       "context": "精通Python编程语言，具备扎实的代码功底..."}
    ]
  },
  "edges": {
    "p_to_t": [                                    // P-[职责描述]→T
      {"position": "AI应用开发工程师", "task": "大模型应用开发与集成"}
    ],
    "t_to_s": [                                    // T-[显式关联]→S（仅原文明确表达时填充）
      {"task": "大模型应用开发与集成", "skill": "编程能力"}
    ]
  }
}
```

**Prompt 关键措辞：** 要求 LLM 优先将实体映射到提供的 Top-K 术语表中，语义一致则使用规范名；无法匹配的标记为 `new_candidate` 并保留原始表述。明确告知"新术语是预期的、有价值的信息"。

**设计要点：**
- Top-K 检索而非全图：K≈30 即可覆盖大部分可匹配术语，且不挤占上下文
- 上下文始终跟随：每个实体的 `context` 保留原始语境，供后续消歧使用
- 不强求推断：`t_to_s` 仅在原文明确表达"用A做B"时填充。文本中隐含的 T-S 关联不在此阶段推断，而是交由图谱层通过跨文档共现统计建立（见 §3.2）
- `match_type = new_candidate` 是合法且预期的输出，支持图谱动态演化

### 2.2 消歧与归一化

按 `match_type` 分三路处理：

```
exact_match ──→ 直接采纳，进入交叉验证队列（大多数实体走此路径）

semantic_match ──→ embedding 验证语义一致性
   ├── 通过 → 采纳 canonical_name
   └── 失败 → 原文+规范名+双方上下文 → LLM 最终消歧

new_candidate ──→ embedding 全图检索最近邻
   ├── 有近邻（Top-K 遗漏的假阴性）
   │   └── LLM 消歧：对比上下文 → 判定合并或确为新实体
   └── 无近邻 → 创建候选节点，标记 source，进入交叉验证队列
```

### 2.3 边的交叉验证

交叉验证的对象是**图上的边**（P-T 边、T-S 边），而非组装好的三元组。每条边独立积累证据、独立验证。

**验证逻辑：**

```
证据积累: 每条候选边的 source_refs 记录所有锚定它的来源文档
   ├── JD 侧的 P-T 边: 来自"岗位职责"段落，强度最高
   ├── JD/论文/新闻侧的 T-S 边: 来自显式关联或共现，强度因源而异

边状态决策:
  ├── 多源独立确认 + 持续出现 → active
  ├── 单源 + 首次出现 → candidate，等待累积
  │     来源为论文/新闻 → 额外标记"前瞻"
  ├── 超时无新证据 → candidate 自动清理
  └── 长期无新证据 → confidence 衰减（未达删除阈值前标记 weakening）
```

边强度计算详见 §3.2。

## 3. 能力模型构建层

### 3.1 图谱 Schema

三类核心节点、两类核心边、两类辅助边：

```
Position（岗位）           Task（任务）              Skill（技能）
├── name, aliases         ├── name, aliases         ├── name, aliases
├── industry              ├── category              ├── category
├── version_history       └── first_seen_date       └── first_seen_date
└── summary

核心边:
  Position -[CONSISTS_OF]-> Task       // 岗位由哪些任务组成
  Task -[REQUIRES]-> Skill             // 任务需要哪些技能

辅助边:
  Skill -[RELATED_TO]-> Skill          // 共现关系（技能簇）
  Task -[EVOLVED_FROM]-> Task          // 任务演化路径
```

**边上属性：**

```
每条边:
  ├── first_seen / last_confirmed
  ├── source_refs: [jd_001, news_015, ...]    ← 可溯源
  ├── confidence: 0.0-1.0                    ← 多源验证得分
  ├── frequency: 0.0-1.0                     ← JD内共现统计（与 confidence 正交）
  └── status: active | weakening | strengthening | candidate

辅助边额外属性:
  Skill-[RELATED_TO]->Skill  ── co_occurrence_strength: 0.0-1.0  // 跨任务共现频率归一化
  Task-[EVOLVED_FROM]->Task  ── transition_period: [first_observed, became_dominant]
```

**技能粒度设计：** Skill 节点定义在"能力类别"层面（如写作能力、数据处理、多媒体技术、交际能力），而非具体工具或技能点（如 Python、PyTorch）。JD 文本中出现的具体工具/技术表述（如"精通Python编程"），在提取阶段（§2.1）由 LLM 通过语义理解归类到对应的能力类别（如→编程能力）——这属于 `semantic_match` 的一种形式：原始表述与图谱中已有能力类别名称不完全一致，但语义上构成归属关系。这一粒度使图谱兼具稳定性——能力类别不随工具迭代而频繁变更——与可操作性，足够支撑人岗匹配与差距分析。

### 3.2 核心边构建策略

**P-T 边**主要来自 JD"岗位职责"段落中 LLM 提取的显式关联（§2.1 `p_to_t`），辅以新闻和简历侧的共现信号：

```
edge_strength(P, T) = w₁·freq(P,T) / freq(P)       // 该岗位JD中任务出现频率
                    + w₂·source_diversity            // 跨源一致性（JD/新闻/简历）
                    + w₃·recency(T)                  // 近期持续出现加权
```

P-T 边的新增或弱化直接反映岗位职责范围的演变。

**T-S 边**有两个信号来源：单文档内的显式关联（原文明确表达"用 X 做 Y"，§2.1 `t_to_s`），以及跨文档的统计共现：

```
edge_strength(T, S) = w₁·Cooccur(T,S) / Cooccur(T)  // 归一化共现频率（主信号）
                    + w₂·I(存在 explicit_link)       // 单文档显式关联（强信号，w₂ > w₁）
                    + w₃·source_diversity             // 共现模式跨源一致性
```

T-S 边的演变追踪技能需求的内部调整——同一任务可能从侧重"写作能力"扩展为需要"写作能力 + 多媒体技术 + 视觉设计"的复合技能簇。

**公式项定义：**

- `freq(P,T)`：岗位 P 的 JD 中提到任务 T 的文档数（薪资加权）；`freq(P)`：岗位 P 的 JD 总数（薪资加权）。比值即岗位 P 中任务 T 的覆盖率
- `Cooccur(T,S)`：任务 T 与技能 S 在同一 JD 中共现的次数（薪资加权）；`Cooccur(T)`：任务 T 与任意技能的总共现次数。比值为归一化共现频率
- `source_diversity`：该边证据覆盖的独立来源类型数（JD / 论文 / 新闻 / 简历），取值范围 [0, 1]，归一化方式为实际覆盖源数除以 4。多源一致的边置信度更高
- `recency(T)`：任务 T 的近期活跃度，`recency(T) = e^(-γ · Δt_last)`，其中 Δt_last 为任务最近一次被确认至今的时间间隔。越近出现的任务权重越高
- `I(存在 explicit_link)`：指示函数，该 T-S 对在任一文档中存在 LLM 提取的显式关联（§2.1 `t_to_s`）时取 1，否则取 0

**薪资加权：** 上述 P-T 和 T-S 公式中的频次统计（`freq` 和 `Cooccur`）均以 JD 薪资为权重进行加权累计，而非简单计数。高薪 JD 中出现的共现信号对边强度的贡献高于低薪 JD——薪资是市场对技能组合价值评估的显式信号。薪资取对数压缩极端值：`weight(jd) = log(1 + salary / salary_median)`。论文和新闻侧数据无薪资字段，使用 JD 侧薪资中位数作为默认权重。

### 3.3 辅助边构建策略

辅助边不驱动图谱核心结构，但为下游任务（差距分析、学习路径规划）提供信息。

**Skill-[RELATED_TO]->Skill**：仅保留 `co_occurrence` 关系：两技能在同一任务的技能簇中高频共现（如多媒体技术 + 视觉设计），边权重为归一化后的跨任务共现频率。能力的兴衰通过需求频率趋势刻画，不需要在能力间画替代箭头。

**Task-[EVOLVED_FROM]->Task**，检测方式：

1. LLM 识别语义相近但需求频率趋势相反的任务对（一个上升、一个下降） 

   > ps. 还有一种确认方式是对应的P/S集合相近

2. 时序验证：新任务出现晚于旧任务，且旧任务频率下降伴随新任务频率上升

### 3.4 演化追踪

```
任务级变更: P-T 边变化（新增/弱化某项任务）
     │
     ▼
技能级变更: T-S 边变化（每项任务内部的技能要求调整）
```

两层边的变化即构成演化追踪的全部记录——P-T 边的增删反映岗位职责范围演变，T-S 边的增删反映任务内部技能要求调整。边的 `first_seen` / `last_confirmed` 时间戳标记变更发生的时间点。

### 3.5 初始图谱冷启动

1. 基础骨架：O*NET
2. 岗位体系：从 JD 侧直接采用招聘平台分类标签，LLM 归一化到统一岗位名
3. 任务体系：从首批代表性 JD 中，LLM 迭代归纳构建
4. 人工审核一轮，生成 v1.0
5. 后续即走动态更新

## 4. 动态更新机制层

### 4.1 增量更新流水线

```
新数据批次
  │
  ▼
① 图谱感知提取（§2.1）→ 产出入库候选节点 + 候选边 + 证据锚点
  │
  ▼
② 消歧与归一化（§2.2）→ 实体链接到图谱已有节点或创建候选节点
  │
  ▼
③ 边证据累积与状态管理（§4.2）→ 每条边独立验证，判定 active/candidate/weakening
  │
  ▼
④ 图谱提交 → version_history 更新
```

核心原则：**软删除不改写历史**、**候选-确认机制**、**每条边可溯源**。

以下 §4.2-4.3 展开步骤③④的具体机制；§4.4 介绍三条贯穿全流水线的全局性处理。

### 4.2 边证据累积与状态管理

每条边独立维护自己的证据链和生命周期，不依赖于其关联的节点或其他边。

**证据追加：** 新批次提取到的边与已有边匹配——若 LLM 提取的实体经消歧映射到已有节点，对应边证据追加到 `source_refs`，更新 `last_confirmed` 时间戳。同一批数据可能同时确认已有边和产生新候选边。

**边状态机：**

```
      首次出现
         │
         ▼
      candidate ──→ active ──→ strengthening（持续有新证据确认）
         │              │
         │              └──→ weakening（长期无新证据，confidence 衰减）
         │                              │
         └──→ 自动清理（超时无新证据）      └──→ 删除（confidence 跌至阈值以下）
```

**状态转换条件：**

- candidate → active：双重阈值——在 N 个独立来源中出现，且在时间窗口 W 内被再次确认
- 来源包含论文/新闻 → 额外标记"前瞻"，N 阈值降低（比如，N≥2 即可激活）
- candidate 超时（T 个时间窗口内无任何新证据）→ 自动清理，不进入图谱
- active → weakening：`last_confirmed` 距今超过设定衰减起点，且无新证据

**置信度双向更新：**

```
衰减（时间驱动）:
  confidence(t) = confidence_0 · e^(-λ·Δt)
  λ 为全局衰减常数，控制边在无新证据时的遗忘速度

强化（事件驱动，新独立来源确认时触发）:
  confidence ← min(1.0, confidence + β)
  β 按来源类型加权：JD > 简历 > 新闻 > 论文
```

衰减与强化互为镜像，确保边在"被持续确认"和"逐渐遗忘"之间双向流动。活跃边保持高位，废弃边自然下沉。

### 4.3 图谱健康巡检

每 N 个批次或每个时间窗口结束时，触发一次全图扫描，检测图结构中的冗余节点。

#### 冗余检测

**背景：** SkillGraph（Li et al., 2026）在 agent 技能库中引入了 Merge 操作——当两个技能节点的图邻居 Jaccard ≥ 0.85 时判定冗余，由 LLM 合并。我们借鉴其思路，适应到静态文本语境。

**适用场景：** 消歧归一化（§2.2）处理了大部分同名异形，但仍有漏网——两个 JD 对同一任务或技能使用了差异较大的表述，embedding 相似度刚好卡在消歧阈值下，各自被当作 new_candidate 入库。例如"品牌传播与推广"和"品牌推广策划"可能指向同一概念。

**检测流程：** 对每对同类型节点（Task-Task 或 Skill-Skill），三项信号并行计算：

| 信号 | 计算方式 | 含义 |
|------|---------|------|
| 名称语义相似度 | 节点名称 + 上下文描述的 embedding cosine | 命名和语境是否接近 |
| 出边重叠度 | `Jaccard(出边目标集)` — Task 看 T→S（需要的技能），Skill 看 RELATED_TO（共现的技能） | 下游关联是否趋同 |
| 入边重叠度 | `Jaccard(入边来源集)` — Task 看 P→T（所属岗位），Skill 看 T→S（需要该技能的任务） | 上游关联是否趋同 |

三项同时高于阈值（如：cosine ≥ 0.85，出边 Jaccard ≥ 0.7，入边 Jaccard ≥ 0.7）→ 标记为候选冗余对。

**为什么必须三项同时检查：** 单一指标各自有假阳性来源——名称相近可能是同义词，出边重叠可能是不同 Task 恰好需要同组 Skill（或不同 Skill 恰好与同组技能共现），入边重叠可能是同一 Position 下恰有不同 Task（或不同 Skill 被同组任务需要）。三者同时高，冗余概率才足够大。

**处置：** 不自动合并。标记的候选对携带三项得分，重新触发 §2.2 的 LLM 消歧流程——此时 LLM 除了原始名称和上下文，还以图邻域重叠度为额外证据做最终判定。

### 4.4 贯穿性机制

以下三项处理并非仅在更新阶段生效，而是作用于数据采集 → 实体抽取 → 边验证 → 图谱更新的全流程。此处集中说明其策略，前述各节中涉及的对应环节以交叉引用标注。

#### 4.4.1 时滞处理

**问题：** 论文侧信号领先 JD 1-3 年，新闻侧领先 6-18 个月。纯 JD 驱动的图谱对新趋势反应偏慢。

**分布差距加权：**

```
weight(s) = 1 + λ · max(0, P_arxiv_news(s) - P_jd(s))

其中 P_arxiv_news(s) 为技能 s 在论文+新闻中的出现比例（该源中出现 s 的文档数/该源总文档数），
      P_jd(s) 为 s 在 JD 中的出现比例。
      当 paper/news 侧提及显著高于 JD 侧时，weight > 1。
```

该权重直接作用于 §3.2 的 `freq` 和 `Cooccur` 计数——在累加时按证据来源区分处理：

- 来自论文/新闻的每条共现证据，在计入 `freq` 或 `Cooccur` 时乘以 `weight(s)`
- 来自 JD 的证据不受影响（对于成熟技能，P_arxiv_news ≈ P_jd，weight ≈ 1）
- 效果：纯 JD 统计下被低估的前瞻技能，其 T-S 边强度被放大，抵消时间滞后

#### 4.4.2 抄袭检测

**问题：** 招聘平台存在大量互相抄袭的 JD，若不加处理，同一份 JD 模板可能被计数为多次独立证据，虚增边 confidence。

1. **预处理**：JD 文本相似度 > 95% → 仅保留最早发布的一条，后续视为副本
2. **结构指纹**：对 JD 提取后的节点有序序列做哈希 + 嵌入相似度比对 → 识别换皮不换骨的模板化 JD

#### 4.4.3 噪声过滤

**问题：** 招聘文本中存在大量不具备区分度的通用表述。

- **样板话术**：TF-IDF / LLM 识别近乎每份 JD 都出现的通用表达（"沟通能力强""抗压能力好""工作认真负责"等），在 Skill 提取中忽略或降权。此类表述频率高但信息量为零

## 附录：后续可扩展机制

以下内容在现阶段算法设计中不纳入实现范围，作为后续迭代的参考方向。移除这些机制的原因是在初版系统中引入会显著增加工程复杂度，而核心价值可通过更简单的方式达成。

### A.1 节点生命周期追踪

**来源：** §3.1 原 lifecycle_stage 定义、§4.3 原生命周期阶段跃迁。

Task 和 Skill 节点可标注生命周期阶段，反映该任务/技能在当前时间窗口的市场需求状态：

| 阶段 | 判定依据 |
|------|---------|
| 萌芽期 | 首次出现，仅前瞻源（论文/新闻）有信号；JD 侧未确认 |
| 增长期 | JD 侧确认，多源交叉验证通过，需求频率上升（△freq > 阈值） |
| 成熟期 | 需求频率稳定在高位区间 |
| 衰退期 | 需求频率持续下降（△freq < 负阈值），连续多个时间窗口 |

任务节点额外存在 **AI替代** 终态：任务整体被 AI 自动化接管（由 Task-[EVOLVED_FROM]->Task 边记录替代路径）。阶段跃迁由 ChangeEvent 记录，支持回溯任一节点在历史时间点的生命周期状态。

**配套机制——边衰减速率差异化：** §4.2 置信度衰减公式 `confidence(t) = confidence_0 · e^(-λ·Δt)` 中的 λ 可按节点生命周期调整——萌芽/衰退期衰减更快，成熟期衰减更慢，使边状态对市场变化的响应更精准。

**不纳入初版的原因：** 生命周期判定依赖多窗口频率趋势的稳定估计，需要充足的时序数据积累；初版可通过边的 `status` 字段（active/weakening/candidate）近似表达节点层面的活跃程度。

### A.2 LIS 前瞻预警体系

**来源：** §4.4.1 原升级方案。

在 Baseline 分布差距加权的基础上，可构建 LIS（Leading Indicator Score）时间序列，追踪论文/新闻侧信号在 JD 侧确认之前的前置窗口。

**实体强度定义：**
```
E_X = 时间窗口内数据源 X 中提到实体 E 的文档数 / 该窗口内数据源 X 的总文档数
其中 E ∈ {T, S}，X ∈ {arxiv, news, jd}
```
实体强度衡量单个实体在特定数据源中的出现广泛程度，区别于边强度（两实体共现紧密程度）。在每批数据完成实体抽取和消歧后直接从提取结果统计得到。

**联合 LIS：**
```
LIS_joint(T, S) = α₁·T_arxiv + α₂·T_news + α₃·T_jd
                + β₁·S_arxiv + β₂·S_news + β₃·S_jd

权重逻辑：α₁ > α₂ > α₃，β₁ > β₂ > β₃（前瞻源权重高，JD 作为锚定基线）
          其中 α₁ > β₁（任务信号的前瞻价值高于技能信号——任务级变化先于技能级）
```

**任务范式级预警：** LIS_T 持续上升而 LIS_S 尚未跟随 → 触发预警。含义——行业在讨论一种新的任务范式（如"Agent 编排开发"），但完成该任务需要的能力组合尚未在需求侧形成共识。

**新岗位发现：** 新岗位在图上表现为新的稳定 P 节点及其 P-T 边簇。触发条件——新 P 节点候选出现、任务技能组合在历史图谱中无对应模式、多源独立确认。离线回放评测验证预测效果。

**不纳入初版的原因：** LIS 需要多源数据的持续采集和足够长的时间窗口才能产生有统计意义的序列；权重校准（Granger causality / 交叉相关）需要大量历史回测数据。初版以 Baseline 分布差距加权实现前瞻信号放大即可。

### A.3 来源质量排序

**来源：** §4.4.3 原本质量差异。

不同数据源的信号可靠性存在差异：JD 侧（显式需求）> 简历侧（自述能力）> 新闻侧（间接提及）> 论文侧（学术前瞻）。当前版本中这一排序已隐含体现在 §4.2 的 β 加权和 §3.2 的 source_diversity 项中。后续可显式建模来源质量评分，结合来源声誉、历史准确率等维度动态调整各源权重。

**不纳入初版的原因：** 初版数据源类型有限（论文/新闻/JD），手工设定的 β 权重足以区分；来源质量排序在数据源扩展到更多类型（如 GitHub、课程大纲、专利）时更有价值。

### A.4 抄袭检测扩展

**来源：** §4.4.2 原后两项。

现阶段保留 JD 文本去重和结构指纹检测。以下两项可在数据规模扩大后引入：

3. **时序抄袭**：后发 JD 内容相似于前发 → 合并为同一证据点，在 `source_refs` 中不重复计数
4. **原创性评分**：综合文本相似度、结构指纹、时序关系给每份 JD 打分，低原创性 JD 在 §3.2 的 `freq` 统计和 §4.2 的 β 强化中降权（如原创性 0.3 的 JD 对边强度的贡献仅相当于一份独立 JD 的 30%）

**不纳入初版的原因：** 初版数据规模下，预处理去重 + 结构指纹已能覆盖大部分抄袭场景；原创性评分的细粒度降权需要更大规模数据标定阈值。
