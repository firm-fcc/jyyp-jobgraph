# 技能熟练度方案介绍（JD 要求侧）

> 版本 1.0 · 2026-08-21 · 量规 `jd_proficiency_rubric_v0.1`　|　代码 `codes/extractor/jd_proficiency.py`
> 本文档人工撰写维护；量规本体见 `codes/extractor/jd_proficiency_prompts.py`，校准报告见 `codes/extractor/output/jd_prof_calibration.md`。

## 一、这个方案解决什么问题

在熟练度方案之前，系统从招聘 JD 中读取的是一张"技能清单"：某岗位要求 Java、要求机器学习、要求团队协作——但**要求到什么程度**没有记录。"熟悉 Java"和"精通 Java"对人才市场是两个不同的信号。

本方案为 JD 中的每个技能要求补上**熟练度等级**（P1-P4/U），使系统能回答这类问题：

- 哪些技能的市场要求正在**水涨船高**（同一技能，2022 年平均要求 P2，2026 年平均要求 P3）？
- 高薪岗位与普通岗位的熟练度要求差多少？
- 对求职者：我的已展现水平（简历侧）与岗位要求水平（本方案）之间有多大差距？

它与同项目**简历侧熟练度方案**共用同一套 P1-P4 等级量表，但语义相反（见第四节），两套结果放在一起即可做"要求 vs 展现"的差距分析。

## 二、等级量表（P1-P4/U）

| 等级 | 通俗含义 | JD 原文示例 |
|------|----------|-------------|
| **P1** | 了解即可：能在指导下做简单常规操作 | "了解 Linux 常用命令" |
| **P2** | 会用：能独立完成定义明确的常规任务 | "熟悉 Java，能独立完成模块开发" |
| **P3** | 用得好：能处理复杂/非例行问题，会比较方案、定位问题、做优化 | "熟练掌握 JVM 调优，负责性能问题定位与优化" |
| **P4** | 精通且主导：制定技术策略/架构方法，影响达系统级或指导他人 | "精通分布式架构，主导技术选型与设计" |
| **U** | 无法判断：JD 只是罗列了这个技能，没有任何程度表述 | "技术栈：Java / Go / Python" |

**U 需要特别注意**：它不是"低要求"，更不是零——只表示"这份 JD 没说清楚要什么程度"。把 U 当作 P1 处理是错误用法。

## 三、四个判断维度（D1-D4）

等级不是拍脑袋给的，LLM 按四个维度分别评估后综合（各维度可因证据不足单独给 U，最终等级不做算术平均）：

| 维度 | 问的问题 | P2 → P4 的阶梯（示意） |
|------|----------|------------------------|
| D1 自主性 | 要求入职者多独立？ | 独立干活 → 自主扛复杂任务 → 主导方案、指导他人 |
| D2 任务复杂度 | 要处理的问题多难？ | 常规任务 → 复杂/非例行 → 高度复杂/跨系统 |
| D3 技术判断 | 要做多深的技术决策？ | 常规选型 → 比较/诊断/优化 → 制定策略/方法 |
| D4 责任影响 | 干好了影响多大？ | 对个人任务负责 → 对核心模块负责 → 对系统/方向有重大影响 |

## 四、JD 侧与简历侧的区别（同一把尺子，两个方向）

量表与维度继承自简历侧（同项目成员交接的冻结量表），但**评估对象相反**，规则因此反转：

| | 简历侧（已有） | JD 侧（本方案） |
|---|----------------|------------------|
| 评估什么 | 候选人**已展现**的熟练度 | 岗位**要求**的熟练度 |
| 证据 | 简历中的行为描述 | JD 中的要求原文句 |
| "精通"一词 | 自我声称，**不可信**，不得抬高等级 | 雇主的明确要求，**一级证据** |
| 年限/职级 | 不得作为依据 | 仅作辅助信号 |
| 防什么 | 简历注水 | 要求通胀（什么都想招最好的） |

两侧共通的一条保守规则：单一"精通"不足以给 P4——P4 需要主导性、复杂性、策略/影响多个信号共同支持。因此 P4 在结果中占比很低（约 2%），这是设计使然，不是漏判。

## 五、判定流程

```
JD 原文
  │
  ├─ 句级技能分类（复用既有抽取层，共享句级缓存 → 证据组装零额外成本）
  │      └─ 产出「技能 → 证据句」映射（逐字原文）
  │
  ├─ 词面锚点提取（精通/熟练/熟悉/掌握/了解 + 年限，正则）
  │      └─ 只做两件事：注入提示词作参考 + 事后一致性复核。不参与定级。
  │
  ├─ ① LLM 量规评估：每条 JD 的技能对（≤6 对/次）按 D1-D4 独立评估 → P1-P4/U
  │
  ├─ ② 严格输出校验：重复键/多余字段/非法等级一律拒绝，整块重试一次
  │
  └─ ③ 确定性旗标：只标记可疑结果供人工复核，不改动等级
         marker_level_conflict    词面与等级差 2 档以上（如"精通"却判 P2）
         marker_span_ambiguous    证据混有多档词面（"精通Python，了解X"）
         p4_without_high_signals  P4 但证据无主导/架构/精通类高信号词
         years_level_conflict     "5 年以上经验"却判 P1
```

词面锚点**刻意不做定级快路**（尽管 81% 的 JD 含熟练度词）：中文 JD 里"精通 Python"的"精通"往往只挂在具体语言（技能点层）上，技能大类的整体要求可能只是"会独立用"——这类判断需要读懂上下文，规则做不到。2026-08 校准抽查证实，LLM 恰恰在这些地方做出了正确的保守判断。

## 六、质量校准（2026-05 窗口，200 JD / 986 个技能对）

| 指标 | 结果 | 解读 |
|------|------|------|
| 等级分布 | P2 40.7% · P3 28.7% · U 23.9% · P1 4.1% · P4 2.4% | 金字塔形；U 主要是软技能套话与技术栈罗列 |
| 词面×等级交叉 | 精通→P3 占 80%；熟悉/掌握→P2 占 66%；了解→P1 占 50% | 与直觉锚点基本对齐 |
| 偏离抽查 | "精通"却判 P2 等 20 余例逐条核查 | 绝大多数是正确判断（精通挂在子技能上），且已被旗标捕获 |
| 严格契约 | 986 对中仅 2 对（0.2%）两次重试后仍失败 | 拒绝坏输出而非静默接受 |
| 成本 | 200 JD 共 256 次 LLM 调用（约 1.3 次/JD） | 证据组装复用缓存；全历史 53 窗口约万次调用级 |

一个典型的"正确偏离"：JD 写"精通 Python/C++，熟悉 Spark，了解 AI 标注"——对技能"程序设计与软件工程"整体只判 P2，因为"精通"修饰的是 Python 这个具体语言，技能大类的整体要求只是独立运用。词面规则会判 P4，这是错的。

## 七、产出与用途

| 产物 | 位置 | 用途 |
|------|------|------|
| 逐对评估记录（含证据句/维度/理由/旗标） | `codes/extractor/output/jd_prof_cache.jsonl`（文本指纹缓存，可审计） | 复查、回溯任何一次判定的依据 |
| 校准报告 | `codes/extractor/output/jd_prof_calibration.md` | 量规调整前的质量审阅 |
| 窗口级熟练度分布 | `data/graph/{窗口}/base/skill_prof.json`（基图重建时自动产出） | 演化分析：技能要求分布随时间的趋势 |
| 人岗匹配接口 | JD 侧 `要求等级` × 简历侧 `展现等级`（同码对齐） | 差距分析：要求 P3 / 展现 P2 = 一档差距 |

## 八、边界与注意事项

- **只评 43 个主技能**：6 个聚合信号技能（主动学习、归纳推理、创造力、抗压、攻坚韧性、严谨诚信）不参与定级——JD 对软技能几乎只写"良好沟通能力"这类无梯度表述，定级无意义。
- **技能 ID 按码连接**：JD 侧与简历侧的技能编码（T-AI-01 等 49 项）已逐一对齐；两边有 20 处中文名差异（我方 2026-08 命名规范化所致），跨侧对接一律按 code，不按名称。
- **数据噪声会传导**：funtype 级 IT 过滤仍有少量非 IT JD 混入（如硬件产线岗）；这类 JD 的技能证据少、多判 U，影响有限但存在。
- **P4 天然稀缺**：若分析场景需要更灵敏的高要求信号，需先放宽量规的防通胀规则并重新校准，不可事后把 P3 顶格当作 P4。
