# 系统介绍

> 面向新加入项目的开发者 · 2026-08-28
> 本文档是对系统全貌的概览性介绍。各模块的接口细节与用法请参阅对应 README 与 `docs/` 下的设计文档。

## 一、这个项目在做什么

这是一套面向信息技术领域的**岗位能力图谱系统**，围绕挑战杯赛题 XH-202621（命题方：科大讯飞）构建。系统要回答的核心问题是：市场现在需要什么样的人才、不久的将来会需要什么样的人才、一个求职者离岗位要求还差多远。

为了回答这些问题，系统从三类来源各异的原始数据出发——招聘 JD、行业新闻、学术论文——用大模型从中提取技能、任务、岗位及其关联，构建一张不断随时间演化的知识图谱。图谱的节点是岗位、任务、技能和技能点，边是它们之间的"构成"和"要求"关系。这张图可以按时间截面切片查看（比如"2026 年 5 月的市场需求"），也可以叠加前瞻信号后做匹配和差距分析。赛题把攻关目标归结为三大难题——新岗位的发现与定义、既有岗位能力的动态更新；招聘数据的"时滞/噪声/抄袭/通胀"治理与"幻觉"防控；简历解析与人岗差距分析。本系统的回应贯穿全文：数据质量治理集中在第五节，新岗位与能力更新的演化机制在第九节，匹配侧的现状与规划在第十一节。

项目的全部代码在 `codes/` 下，按九个子项目组织，形成一条从数据采集到图谱合成的完整流水线。分类体系（岗位/任务/技能/技术栈）构建产物在 `classify/` 下。设计文档和可读介绍在 `docs/` 和 `introduction/` 下。

对初次接触本系统的人，建议的阅读与上手路径是：先读本文第二、五、八节，建立"基图与叠层、数据质量治理、逐窗流程"三块核心认知；需要了解代码时按第六、七节的模块说明对号入座；运行层面，处理一个新窗口只需一条命令（`python codes/graph/run_pipeline.py --window YYYY-MM`），各阶段产物的位置与校验方法见 `codes/graph/README.md`，当前进度与待办见 `docs/roadmap.md`。

## 二、核心设计：基图与叠层

系统最重要的设计决策是把图谱分成两层，各自独立构建、独立调参，最后合成。

**基图（G_base）** 只从招聘 JD 构建，回答"市场现在需要什么"。JD 里的岗位要求和技能清单是客观的市场事实——企业愿意为某种能力付钱，这件事本身就比论文里的趋势预测更有统计说服力。基图的边权重来自 JD 数据中的频次统计，施加薪资加权和历史衰减。

**叠层（ΔG）** 从论文和新闻构建，回答"市场将要需要什么"。学术论文反映技术萌芽（领先 JD 约 1-3 年），行业新闻反映产业采纳（领先 JD 约 6-18 个月）。叠层不修改基图，而是在基图的边上叠加一个修正权重，使前瞻信号能体现在最终的匹配结果中。JD 侧也参与叠层，但角色是"市场确证"——当前瞻信号终于在 JD 中出现时，说明市场已经为它付费了，这是信号"转正"进入基图的硬条件。

两者的合成关系很简单：`G_eff = G_base ⊕ ΔG`，即每条边的有效权重等于基图权重加叠层修正。合成只在独立的 `effective/` 层完成，绝不回写基图或叠层，因此基图可独立使用，叠层可插拔、可独立调参。

这种分离带来一个重要性质：基图分类永远使用固定的体系基准，叠层热更新只发生在叠层内部——两者互不干扰，可以并行计算。

## 三、四层能力体系

图谱的节点按四层组织，从上到下越来越具体：

岗位（Job）是招聘市场上可识别的职位名称，如"NLP 算法工程师""前端开发工程师"。系统当前收录 131 个 IT 岗位，归入 9 个一级类别。

任务（Task）是岗位由哪些工作职责构成，如"大模型应用开发""系统运维""软件测试"。当前的 27 个任务是从 JD 中 LLM 归纳并经人工校验得到的抽象类别。

技能（Skill）是完成工作所需的能力类别，如"机器学习与深度学习""程序设计与软件工程""团队协作与协调"。技能跨越数年不变，是匹配分析的主要层面。当前的 49 项技能融合了 O*NET、CS2023、新加坡 IMDA 生成式 AI 框架等多源文献。

技能点（SkillPoint）是具体的工具、框架、语言，如 Python、PyTorch、Kubernetes。技能点随技术迭代快速更替，与技能是多对多关系——Python 同时属于"程序设计与软件工程"和"数据分析与可视化"。技能点层是开放集合，新工具随 JD 出现不断进入，因此配有归一体系——同一技术不因命名差异分裂成多个节点，并带语言/框架/库等十三类呈现分层标签（详见 graph 一节）。

这四层之间的边有四种：岗位→任务（J-T，岗位由哪些任务构成）、岗位→技能（J-S，JD 中直接陈述的能力需求）、任务→技能（T-S，任务推导出的能力需求）、技能→技能点（S-SP，能力包含的具体技术）。

此外还有一个正交的**技术栈**维度（TS-01 到 TS-08，如"前端与用户体验""AI/ML 与数据智能"），它不是纵向体系的一部分，而是给每条 JD 打的横向标签，支撑赛题"按技术栈切换视图"的需求。

## 四、三类数据源

三类数据在系统中的角色各不相同，理解它们的时间特征和信号强度是理解整个架构的关键。

**招聘 JD** 是基图的唯一构建来源，也是叠层的"确证源"（权重 1.0、半衰期 365 天）。数据来自 51job，本地库共约 590 万条（2021 年 6 月至 2026 年 5 月，53 个月度窗口）；进入图谱前先经岗位归类严格门与范围过滤，大窗口按需降采样（见 graph 一节）。JD 反映市场当前需求，但滞后 3-12 个月。系统从每条 JD 中用 LLM 提取它涉及的技能、任务和技能点，统计频次来构建图的边。JD 中还会判定每个技能的**熟练度要求等级**（P1-P4/U），使系统能区分"了解 Java"和"精通 Java"。

**学术论文** 是叠层的主信号（论文档位权重 S 档 1.0 / A 档 0.7、半衰期 730 天）。数据来自 arXiv 文献图书馆，按赛题六专题筛选，本地保留 S/A 两档唯一论文共 10,370 篇——六专题语料 8,097 篇（2023-07 起，含全文），2022 年全库分档批次 2,273 篇（S 51 / A 2,222，2022-01 起至 2022-12，含元数据与摘要）。论文反映学术萌芽，领先 JD 1-3 年。系统从论文中识别两类信号：一是"新信号"——论文中提到但当前体系里还没有的技能/任务/岗位；二是"提及"——论文对既有体系实体的引用，这会让既有实体的叠层强度增强。

**行业新闻** 是叠层的辅助信号（权重 0.4、半衰期 180 天）。数据来自 33 个公众号和技术媒体共 282,945 篇文章（2026-08-30 zip 全量入库后；其中 36氪快讯约 18 万篇，经相关性过滤筛除噪声）。新闻反映产业采纳，领先 JD 6-18 个月，但信号噪声大、时效快，因此权重和半衰期都低于论文。新闻先经 LLM 相关性过滤（标题+导语），只保留相关文章进入后续信号提取。

三类数据的权重差异体现了设计意图：论文萌芽最早但最不确定，新闻采纳更近但仍属前瞻，JD 确证最可靠但已滞后。叠加衰减机制后，一个信号从论文中出现、经新闻跟进、到 JD 确证，其强度会随时间先升后稳——直到 JD 确证足够强时触发"转正"，进入基图。就时序覆盖而言，论文与新闻按**月度增量**进入叠层——窗口 W 只消费 W 月发表的文档，更早月份属其自身窗口（叠层纪元之前的语料即预史，不入场）：新闻与论文均自首个叠层窗口 2022-07 起逐月进入。

## 五、数据质量治理：对赛题核心关切的系统回应

赛题把"时滞、噪声、抄袭、通胀"并列为招聘数据的四大质量难题，要求以多源异构数据清洗与交叉验证融合机制回应，并防控大模型生成内容的"幻觉"。这些关切在系统里不是由某个单独模块处理的，而是分布在从数据入口到图谱合成的整条链路上——本节把它们集中说清楚。

**时滞——被建模为系统的骨架，而不只是被消除。** 三类数据按真实时间戳（JD 的发布时间、论文与新闻的发表时间）月度分桶、逐窗回放，系统按数据到达的顺序处理每一个月，时滞本身成为实验框架而非需要掩盖的缺陷。在此之上，三类源配置了不同的时间常数：论文信号半衰期 730 天（学术萌芽持续久）、新闻 180 天（产业消息时效快）、JD 365 天（市场确证），快照统一以窗口末为基准重算强度，旧证据自然衰减。更进一步，系统把时滞变成可度量的量——合成时计算的 gap（叠层强度减去 JD 频次）直接衡量"学术已热、市场未跟"的滞后程度，λ 修正把前瞻信号提前注入有效图，而"转正必须积累 JD 确证"定义了滞后的收敛点。跨窗口频次则以 α=0.85 的衰减链累积，近期月份权重更高。

**噪声——六层防线贯穿全流程。** 数据入口层做第一道过滤：文本指纹精确去重（实测全量约 29% 的行是重复文本）、岗位归类严格门（泛词关键词命中一律送 LLM 按内容复核，防"测试"误中产线测试岗）、岗位范围过滤（技能体系覆盖不足的 34 个岗位整类排除）、无任何技术信号的 JD 降级剔除。抽取层：分句时跳过福利/公司介绍等噪声段（实测约 4% 句），句级缓存保证"同证据同判定"，LLM 输出经严格契约校验。统计层：大窗口降采样用逆概率加权保持无偏，抽样损伤经蒙特卡洛验证不超过 0.3% 边权重。叠层信号层：新信号候选设文档频门槛（随机搭配进不来），保存时剔除低强度的一次性噪声（多证据信号永不删除），并按置信度分级计权。生命周期层：强度低于 0.15 的实体休眠——不参与下次更新但完整保留、可被新证据唤醒，噪声信号自然沉底。新闻源因本身噪声大，专门设计为低权重 0.4 加 LLM 相关性过滤（实测通过率约六成）——降权而非删除，是对高噪声源的恰当态度。

**抄袭——精确与近重双重去重。** 逐字复制（同文多投、多站点转发）由归一化文本指纹解决，每种内容只计一次。换皮微改（改公司名、薪资或标题后重发的模板帖）则由专门的近重复过滤阶段处理：对每条 JD 的去噪正文计算 3-gram simhash 指纹，分块索引召回候选对后用 Jaccard 相似度（≥95%，对应赛题"相似度>95%"口径）复核确认，抄袭簇只保留最早发布的代表，其余变体在采样分母、抽取输入、基图聚合、叠层扫描、汇总导出五个环节统一剔除。实测两个正式窗口约 7% 的 JD 是换皮变体；更早对 50 万条近期数据的重复分析里，极值是同一条模板跨八个月被反复发布 1,007 次——不去重的话，这类模板帖会按重复次数虚增频次与边权重。同文跨月重发按"当月在场"计入各月（这正是逐月 presence 统计想要的语义），跨月合并证据点留作二期。

**通胀——要求通胀由熟练度量规正面回应。** 招聘文本的通胀表现为"精通""资深"泛滥、要求罗列虚高。系统判定 JD 熟练度要求时遵循 precision-first：单一"精通"字样不足以定 P4（最高档），需要多个高信号梯度词共现；无梯度表述的罗列一律判 U（最低档），软技能（沟通协作类）无梯度证据时免 LLM 直接判 U。P1-P4 的分层本身就是把通胀的要求文本还原为可区分的信号层次——校准实测 P2/P3 合计约七成、U 约两成，符合真实 JD 的要求梯度分布。

**幻觉防控——确定性优先与证据约束。** 系统的通用策略是"能确定性解决的不交给 LLM"：技能点归一先走字面折叠与人工注册表，LLM 只裁决首见的未知名；新信号发现先走词表差集与 n-gram 时间差分，LLM 只裁决频次过槛的残差候选；岗位归类先走岗位名匹配与词库快路，LLM 只复核可疑命中。交给 LLM 的部分则有三重约束：提示词注入量规、类别判定规则等防歧义契约；输出经严格契约校验（拒绝多余字段、非法枚举、数量不符），可疑结果打确定性旗标而非静默接受；关键产物强制携带证据句与文档溯源，快照与合成层可回查每条边的证据来源。体系热更新还设有独立的监督 Agent 拦截不必要提案——历史上曾因此拦下任务数失控膨胀至 194 的提案洪峰。

**交叉验证——三源互证是转正的硬条件。** 论文提出前瞻信号、新闻跟进放大、JD 出现确证证据；三源按时间戳合并，跨源同名条目的证据取并集、强度按判源重算。一个新实体要进入基图必须同时满足强度门槛与"至少 2 篇（岗位 3 篇）不同 JD 文档的确证"——学术说了不算，市场付了钱才算。这是对赛题"多源异构数据清洗与交叉验证融合机制"最直接的回应。

## 六、系统组成与数据流水线

整个系统在 `codes/` 下按九个子项目组织，按数据流的方向可以串成一条清晰的流水线。下表先给一个速查，后面逐个说明。

| 模块 | 职责 | 是否调用 LLM |
|------|------|-------------|
| `job_classify_51job/` | 从 51job 职能分类中判定 IT 岗位 | 是 |
| `jd_fetch/` | 从 MySQL 抓取 JD，按 funtype 过滤导出 CSV | 部分需 LLM |
| `jd_annotate/` | JD 标注（技术栈/级别）与岗位体系构建、归类引擎 | 是 |
| `paper_signal/` | 解析论文 TXT 为结构化记录 | 否 |
| `news_signal/` | 解析新闻 TXT 为结构化记录 | 否 |
| `extractor/` | 分类抽取：JD 技能/任务/熟练度 + 论文/新闻信号分类 | 是 |
| `builder/` | 体系构建/热更新 + 三源 ΔG + 叠层生命周期 | 是 |
| `timeline/` | 时间线编排：JD 按月分文件 + 新闻/论文映射表 | 否 |
| `graph/` | 图谱快照 + 基图边计算 + 图谱合成 | 基图边计算需 LLM |

数据流的主干是这样的：51job 的原始职能分类先经 `job_classify_51job` 判定哪些是 IT 岗位，再由 `jd_annotate/build_jobs.py` 重构成岗位体系 v2（131 岗位）。`jd_fetch` 用这个体系过滤 MySQL 中的 JD 数据导出 CSV。`jd_annotate` 还负责给每条 JD 标注技术栈和级别，以及把每条 JD 归类到具体岗位。

论文和新闻各自先经 `paper_signal`/`news_signal` 解析成结构化记录（不含 LLM），然后进入 `extractor` 做分类——提取新信号、识别对既有体系的提及。分类结果交给 `builder` 做叠层 ΔG 热更新。

`timeline` 把三类数据按时间戳统一编排，供图谱按时间顺序导入。`graph` 模块构建时间截面快照、计算基图边、合成 G_eff。`builder` 还负责叠层的生命周期管理——可见性门控、遗忘、转正。

## 七、代码模块详解

### job_classify_51job

这是岗位体系构建的第一步。51job 的职能分类树有 1584 个节点，系统用 LLM 逐节点判定是否属于信息技术领域（带置信度），最终得到 255 个 IT 岗位。这个结果后来被 `build_jobs.py` 重构成 v2 体系（131 岗位），所以本模块的产物主要是历史存档，但它建立的"funtype → IT 判定"映射至今仍是 JD 过滤的基础。

### jd_fetch

从 MySQL 数据库抓取 JD 并导出 CSV。数据分两批：2025-2026 批来自远端 job51 库（50 万条 IT JD），JD-Origin 批来自本地导入的早期数据（540 万条）。每条 JD 的 `funtype` 字段（51job 平台的职能分类标签）支持 `"A or B"` 多值，任一部分判定为 IT 就保留。这个模块的 `import_origin.py` 负责把 19GB 的 `.zst` 全库 dump 流式导入本地 MySQL，`rebuild_it_map.py` 负责在映射文件丢失时重建 funtype→IT 映射。当前数据已全部落库，没有增量拉取任务在排。

### jd_annotate

这个模块承担三类职责。第一是构建技术栈体系——人工确定的八类技术栈（前端、后端、数据存储、中间件、基础设施、安全、DevOps、AI/ML），落盘为 `techstacks.json`。第二是给每条 JD 标注技术栈（多标签 1-4 类）和级别（L0 实习到 L4 专家五档），标注引擎三层解析（标题词库→正文词库→LLM 缓存），标注时零 LLM。第三是构建岗位体系 v2 和 JD→岗位归类引擎 `classify_job.py`，引擎用四路信号归类：岗位名匹配、词库快路、LLM 兜底、任务/技能向量比对。非 IT 域 JD 由 LLM 显式输出"非IT相关"标签，下游可据此跳过。2026-08-25 起生产口径改为**严格门**——仅岗位名出现在标题直接采信，关键词命中因泛词误报多（"测试"可误中产线测试岗）一律送 LLM 按内容复核，LLM 批间并发；一个窗口归类跑满后落窗口级缓存 `{窗口}.jobcls.json`，下游降采样与抽取直接读缓存，免重复扫描大文件。

### paper_signal

论文数据处理层，纯解析、不调 LLM。它把论文 TXT 文件（开头有 arXiv ID、标题、发表日期等元信息头块）解析成 `PaperRecord` 对象，包含标题、关键词、摘要、正文片段和证据句。解析层用双启发式提取摘要（先找显式 `Abstract` 标记，找不到再用前向/后向扫描兜底），并支持跨专题同文去重（一篇论文命中多专题时文件逐字节相同，按文件名+md5 去重防止重复计权）。模块用唯一命名（`paper_config` 而非 `config`），避免被其他模块跨目录导入时产生冲突。全库分批交付的论文（如 2022 年批次）为 arXiv 元数据裸格式，由本模块的 `arxiv_ingest.py` 以批次索引 xlsx 为权威字段源转换成标准头块格式后并入 `data/papers/`，B/C 档不入库。

### news_signal

新闻数据处理层，与 `paper_signal` 对称。解析公众号 TXT（头块含标题、链接、发布时间、公众号名，其后为正文）成 `NewsRecord`。本模块还包含一个一次性的 `convert_docx.py`，把 5427 篇公众号历史文章 .docx 转成 news_raw 约定的 TXT 格式。同样用唯一命名避免跨模块冲突。

### extractor

分类抽取层，是系统中调用 LLM 最频繁的模块，负责从各类文本中识别和分类技能、任务、岗位。

对 JD，它把文本分句后逐句送 LLM 分类——每句话涉及哪些技能、哪些任务，技能点严格限定为工具/框架/语言等具体技术实体。分类结果按句级缓存（`cache/cache_{mode}.jsonl`），同一句话只调一次 LLM。批量送入（每批 15 句）摊销成本、批次按 `llm.concurrency`（默认 20）并发，关闭推理模式提速。除技能/任务频次外，还产出技能→技能点映射字典。生产用 **merged 模式**——同一子句一次调用同时出 skill+task+skillpoint（替代 skill/task 两次分离调用，句级 LLM 调用减半、不损穷举性，缓存按 prompt 版本隔离，现为 `cache/cache_merged_v2.jsonl`）；并对 JD 分段跳过福利/公司介绍等噪声段（实测约 4% 句、干净无损），技能点口径收紧为可独立学习/可考核的技术载体并显式排除品牌、产品型号、设备仪器与泛指词。

对 JD 中的熟练度要求，模块用移植自简历侧的量规方案逐 (JD, 技能) 对评估等级 P1-P4/U（U 表示"仅罗列无梯度表述"）。三段防线保证精度：量规注入提示词、严格输出契约校验（拒绝重复键/多余字段/非法枚举）、确定性正则旗标复核（只标记可疑结果，不改动等级）。词面锚点（精通/熟练/熟悉等）不作定级快路，只作提示和事后一致性复核；生产管线上软技能无梯度表述的证据直接判 U（免 LLM），下游匹配按最低档要求对待。校准结果：P2 占 40.7%、P3 占 28.7%、U 占 23.9%，契约失败仅 0.2%。这套熟练度评估语义与简历侧相反——JD 中"精通"是雇主的明确要求属一级证据，但防要求通胀（单一"精通"不足以给 P4）。详细介绍见 `introduction/技能熟练度方案介绍.md`。

对论文，它做两件事：一是**提及识别**——识别论文对既有技能/任务/岗位的引用（复用 JD 抽取的分句/缓存/LLM 设施）；二是**新信号分类**——提取论文中提到但体系里还没有的技能/任务/岗位，然后做体系映射（判断是映射到既有条目、合并进相近条目，还是判定为新实体）。

对新闻，它先做**相关性过滤**（LLM 判别标题+导语，只让相关新闻进全文），再做**信号提取**和**提及映射**。相关性过滤不设关键词硬门槛——因为新信号天然在词表之外，实测关键词门槛会丢弃 44% 的语料，其中 23% 实为相关。

### builder

体系构建与热更新层。它的任务体系构建采用"提案 Agent → 监督 Agent → 应用"的迭代精化模式：冷启动时用分层抽样 500 条 JD 让 LLM 归纳出初始体系，热更新时多轮投喂新数据让 LLM 提案新增/合并/修改，监督 Agent 拦截不必要的提案。全量 590 万条 JD 跑 LLM 成本过高，故用分层抽样替代——按岗位大类分层、按文本去重（实测 32% 重复）。热更新曾出现过任务数失控膨胀至 194 的教训（从 28 合理类别涨到 194，含重复名和粒度崩成岗位名），根因是提案过提案、监督过批准、无去重——后通过加粒度契约、映射先行、同名防重、程序化过滤等手段修复，最终稳定在 27 个任务零新增收敛。

builder 还承接三源 ΔG 增量层热更新。论文 ΔG 流水线（`paper_delta.py`）从 `paper_signal` 取解析结果、从 `extractor` 取分类结果、在本层聚合进 `classify/DeltaG/papers_delta.json`。新闻 ΔG 流线对称。论文与新闻的新信号都要过**两道映射裁决**：初判（映射先行、下位概念视为已覆盖、跨文档合并、粒度拒绝）之后，判为"新任务/新技能"的候选还要过一道独立的**守门终审**——换一个"守门员"视角复核（基调宁严勿宽、宁映射勿新增），被既有体系涵盖者当场改判映射，同域兄弟环节（采集/标注/构建、容灾/切换/监控这类同一对象的不同侧面）合并归簇，确无涵盖者才落叠层并记审计理由；多数研究级短语由此落到正确归宿——既有条目的提及级增强证据（strengthenings），而非新条目。JD 侧 ΔG（`graph/jd_delta_v2.py`，2026-08-27 起替代旧的 100 条抽样投喂）是市场确证源，采用**采样基面确定性扫描 + 残差 LLM 裁决**：数据基面与整条管线一致——就是 Stage S 降采样后的选择集（采样是成本所致的数据量限制，图谱的一切产物只能来自基面内数据），确定性部分对基面内全部 JD 做已知词表差集（英文 token 通道）与中文 n-gram 时间差分（Apriori 逐级上卷、df 带宽、碎片归约），LLM 只裁决频次过槛的残差候选（复用热更新引擎 propose→supervise→apply 纪律，结论跨窗缓存）。裁决落点四种、映射最优先，但**只有全新任务/技能会写入叠层**——这是 JD 侧体系级演化的唯一发现通道：判定为全新任务/技能的候选要过一道独立的**新颖性复核**，换一个"守门员"视角对照基线逐条排除（基调宁严勿宽、宁映射勿新增），被涵盖者当场改判为对既有任务/技能的涵盖式映射（同物异名、上下位包含、近义指称，如"前端开发"映射入"应用软件开发"），确无涵盖者才作为新实体落叠层并记录"最接近条目 + 为何不涵盖"的审计理由，复核未决者留待下窗重试。技能点与涵盖式映射的判定只入跨窗缓存排水、不写叠层——技能点的发现权威在基图构建阶段的句级抽取与三层归一，被涵盖短语的市场存在已由基图无偏统计。对叠层参与实体的确证在基面内字符串预筛后送 LLM 判定"要求掌握"；这类 require 级证据才是转正所计的"确证"，发现通道的扫描证据只贡献强度、不算确证。基线提及跳过（避免与基图频次重复计权）。论文 ΔG 还有一个 Stage C——把论文对既有体系的提及直接并入 strengthenings（叠层增强修正），使前瞻信号能直接增强基图实体的权重。

叠层生命周期管理也在 builder 中。`participation.py` 做可见性门控——强度低于 0.15 的叠层实体休眠（不参与下次更新但永不删除），`promotion.py` 做转正——强度达 0.25（岗位 0.30）且 JD 确证文档数达 2（岗位 3）时（"确证"专指确证通道判定"要求掌握"的 require 级证据，扫描发现类证据不计——市场措辞里"出现过"不等于"要求掌握"），先自动备份再写入基准体系文件，标记 `graduated` 后下窗口快照移出叠层。

`job_hot_update.py` 是岗位热更新模块，消费 ΔG 中 `pending` 状态的新岗位，用 LLM 分析其提及文本提取任务/技能关联，回填 `related_tasks`/`related_skills`，使新岗位不再是孤立节点。

### timeline

时间线编排器，纯标准库、零 LLM。它把三类数据按时间戳统一编排：JD 按 `opentime` 月份重新分组为月度 CSV 文件（53 个月度文件，2021-06 到 2026-05），新闻和论文各生成文件→时间戳映射表。时间戳复用各自的解析层（`paper_parser`/`news_parser`），保证与下游 ΔG 处理使用同一日期。这个模块的产物供图谱按时间顺序导入。

### graph

图谱层，把前面所有模块的产物组装成最终的知识图谱。快照、基图边、合成是它的三类核心产物，此外还有技能点归一与参数重放两个支撑机制。

**快照构建**（`snapshot_builder.py`，零 LLM）：把体系 JSON 原样拷贝为基图节点，把三源 ΔG（论文/新闻/JD）合并为单层叠层。合并时按归一化名称跨源分组、证据按文档 id 去重、强度按来源权重和半衰期以窗口末为基准重算。已转正的条目移出叠层视图，可见的条目附 `participates` 标记。

**基图边计算**（`base_builder.py`）：全量生产走**逐窗时序**流线（S0→A→D0→S→B→C→D），由 `run_pipeline.py` 一键编排、各步幂等断点——它模拟数据到达的顺序，也是后续月度更新的固定流程。

最前面是 S0 大窗预抽样（`jd_pre_sample.py`，2026-09-03 起）：只有窗口唯一文本指纹超过 6 万的"巨窗"才触发——确定性哈希预选 6 万条再进入后续流程，A 门的 LLM 成本随之上限封顶，逆概率因子复合进 S 的权重保持总量无偏；未触发的窗口（绝大多数月份）零行为变化。

前两步是入口过滤。A 岗位归类门先用严格门与岗位范围过滤（`graph/it_scope.json`）圈定 IT 池——硬件/半导体、通信现场/设备、数据标注等 34 个岗位因 49 技能体系覆盖不足而整类排除（归类引擎见 jd_annotate 一节）；D0 近重复过滤（`jd_dedup.py`）接着识别换皮抄袭簇——正文 simhash 指纹加 Jaccard 复核，簇内只保留最早发布的代表，实测两个正式窗口约 7% 的 JD 是抄袭变体。

中间两步决定成本与覆盖。S 按需降采样（`jd_sample.py`）在窗口 IT 超上限时做岗位分层封顶抽样：比例分配之外设稀疏岗保底（floor），确定性哈希保证选取可复现、扩量时原键全保留，逆概率加权使窗口频次仍是总体的无偏估计——蒙特卡洛验证抽样损伤不超过 0.3% 边权重。B 句级抽取（`run_jd_extract.py`）采用两遍式：先收集全窗唯一句批量并发分类，再逐 JD 组装结果；merged 模式一次调用同时产出技能、技能点与任务，分段跳过福利等噪声段，无任何技术信号的 JD 降级剔除。

最后两步产出图。C 熟练度（`run_jd_proficiency --from-vectors`）按 (JD, 技能) 对、经证据级跨 JD 去重后定级，回填 `skill_vec_prof`；D 聚合消费源文件重建每 JD 的集合，零 LLM 地算出基图。A/B/C 三阶段的 LLM 批次均按 `llm.concurrency` 并发，批级容错保证单批瞬时失败不中断整窗。

每窗产物落 `data/timeline/jd_derived/`（分类向量源文件及元信息，与源数据目录分离）：基图四种边、`entity_freq.json`（E_jd，合成 gap 用）、`skill_prof.json`（熟练度分布）和 JD 多维汇总 CSV（`data/graph/data/jd_summary_{窗口}.csv`，每 JD 一行、各项用中文名，标准岗位列为 `std_job`）。统计频次可施加薪资加权（Stage D 组装期按窗口中位数现算 `log(1 + 月薪/中位数)`，经 `graph_base.salary_weight` 开关、改后重放即生效），跨窗口频次衰减链累积（`freq = freq_new + α·freq_hist`，α=0.85）。熟练度无法判级（U）时，人岗匹配约定按最低档要求对待。无源文件时回退旧路径（字符串 funtype 门 + 200 抽样 + LLM 抽取，保既有窗口兼容）。

**技能点归一体系**：为防止同一技术因命名差异（大小写、中英文、简称、版本号）分裂成多个技能点节点，B 阶段在抽取清洗后做三层归一——字面折叠（零成本统一大小写与分隔符）、人工审定注册表 `skillpoint_registry.json`（规范名 + 别名 + 类别，类别判定规则注入首见归一提示词，含"标准=认证与管理体系而非技术规范"等防歧义条款）、LLM 首见归一（未知名判定并入既有规范名或登记新实体，判定结果缓存跨窗复用，可人工复审后提升进注册表）。硬口径：只合并同一技术的命名变体，不同代际与组件保持独立（Spring ≠ Spring Boot、AngularJS ≠ Angular）；版本号并入母项（HTML5→HTML、ES6→JavaScript），书写惯例如 C/C++ 展开为 C 与 C++ 各计一次。实测两个正式窗口的唯一技能点从 5,022 收敛到 3,899，TOP100 高频技能点跨窗完全一致。

**图谱合成**（`synthesis.py`，零 LLM）：计算 gap（叠层强度超出 JD 频次的部分），在基图边上叠加 λ 修正，把岗位关联边转为 G_eff 新边，对双端都有 gap 的任务-技能对合成新边。合成结果只写 `effective/` 层，绝不触碰 base/ 或 delta/。

**参数重放**（`replay.py`，零 LLM）：基图聚合、快照强度重算与合成是参数化纯函数，调整组装类参数后一条命令按时间序整链重建；每份产物记录参数指纹，可追溯生成它的参数集（幂等性已实证——重放产物与正式运行逐字节一致）。

整个图谱按时间截面组织存储——每个时间窗口一个文件夹，内含 base/delta/effective 三个子图。任意时间截面自包含，可直接加载无需重放历史。

## 八、图谱构建：从数据到知识图谱

把上述模块串起来，一个时间窗口（比如 2026 年 5 月）的完整处理流程是这样的：

首先是时间线编排，把新数据按月分桶、生成映射表。然后四条线可以并行推进：JD 分类做基图边计算（基图统计）、JD 侧 ΔG 做市场确证、论文 ΔG 提取前瞻信号、新闻 ΔG 提取辅助信号。四条线互不干扰——JD 分类用固定体系基准不读叠层，三条 ΔG 管线各写各的源文件互不覆盖；三条 ΔG 均支持逐窗增量（`--window` 只处理窗末前到达且未处理过的文档，参与门标签空间以窗末为基准，体系后续演进不泄漏进历史窗口）。岗位热更新在 ΔG 之后、快照之前做——消费 pending 新岗位回填关联。

四条线完成后构建快照（三源 ΔG 合并 + 体系节点），接着做基图边计算（如果快照已保留基图边则跳过），然后图谱合成生成 effective 层，最后校验。转正收口在合成之后做——强信号加 JD 确证达标的叠层实体写入基准体系，作用于下一个窗口。

这条流线在工程上做成了**两层分离**：LLM 阶段的产物（jd_vectors 源文件、三源 ΔG 的原始证据、句级与证据缓存）是不可变的"证据层"，一次付费终身复用；基图聚合、叠层强度重算、图谱合成是参数化的"组装层"纯函数。因此调整组装类参数（强度权重、半衰期、生命周期门槛、α 衰减、λ 合成系数、薪资加权）后，用 `replay.py` 一条命令即可按时间序零 LLM 地重建全部窗口的基图、快照与合成图（已验证逐字节幂等）；每份产物记录参数指纹，可追溯它是哪套参数算出来的。

这个流程的每一步都幂等或断点化，任意一步失败重跑不会产生脏数据。JD 侧的逐窗时序已由 `run_pipeline.py` 一键编排；跨模块的全流程 Orchestrator 自动调度尚未实现（属 roadmap P2），按 `docs/loop-design.md` 的步骤顺序手动执行即可。

## 九、叠层生命周期：信号的生长与转正

叠层不是一张静态清单，而是一个有生命周期的信号池。一个新信号从论文或新闻中被发现后，会经历五个状态。

新证据使它**诞生**并进入活跃态——只要强度达到 0.15 的参与门槛，它就参与后续窗口的更新，进入 JD 侧确证通道的目标清单。**出生以体系学习时序为准**（入场窗戳，而非证据日期）：体系在某窗首次录入一个信号，市场确证就必须来自之后窗口的数据——一次性回填的旧语料（如整年并入的论文库）不会因为证据日期早而提前确证，首个叠层窗口因此必然没有任何转正候选。基图抽取分类则始终使用固定体系基准，叠层不进基图标签空间。反复出现时，证据用 noisy-OR 跨文档累积（独立证据越多，合并后的"出现概率"越高，任何单条证据都不足以一锤定音），强度单调上升（**增强**）。如果一段时间没有新证据，半衰期衰减使强度下降，跌破门槛就**休眠**——失去可见性、不参与下次更新，但条目和证据完整保留在 ΔG 文件中，可以被新证据唤醒（**遗忘是降级而非删除**）。

当强度足够高（≥0.25，岗位 ≥0.30）且 JD 侧出现确证（≥2 篇 JD，岗位 ≥3 篇）时，信号**转正**——写入基准体系文件，成为基图的一部分。转正是唯一的自动基图演化通道：手动切换 `taxonomy_base.json` 是新纪元（旧窗口不回填），转正是在纪元内的渐进演化。转正作用于下一窗口——本窗口快照保持转正前的历史视图，下一窗口的快照自动跳过 graduated 条目，基图边自然产生。

这个机制保证了前瞻信号不会永久占据叠层（衰减清理未被确认的信号），也不会过早进入基图（需要市场确证）。转正前出错的回滚也很简单——写入前的三基准文件自动备份在 `classify/backup/` 下，整目录拷回即可。

**新岗位的完整旅程**（对应赛题"新岗位发现与定义"）：新岗位候选由论文与新闻的前瞻信号提出（JD 侧不从零发现新岗位——岗位体系沿用 51job 分类，避免把公司自创头衔误判为新职业），进入叠层后标记 pending；岗位热更新模块随即用 LLM 分析其全部提及文本，回填任务与技能关联，使候选岗位具备"名称—核心职责—必备技能"的定义结构；达到转正门槛（强度 0.30 + 3 篇 JD 确证）后写入岗位体系（GJ- 编号、定义、关联边、funtype 挂载），从此参与归类与基图构建。人工优化与动态更新有两个入口：转正前直接编辑叠层条目（ΔG 文件即审即改），转正后走体系文件（版本化基准 + 转正备份，任何历史可回滚）。

**既有岗位能力的动态更新**（对应赛题第二项核心功能）：逐窗时序使每个岗位的能力画像自然演化——边权重随窗口频次变化，技能点集合随新技术出现而增减（每个技能点节点记录出现窗口序列），熟练度要求分布逐窗产出（`skill_prof.json`）。两个相邻窗口的对比即是"新增/删除/修改"能力项的清单。每次更新都携带数据源：基图侧可回溯到具体 JD（jd_vectors 逐条溯源，且近重复过滤保证了证据独立性），叠层侧每条修正携带证据句与文档 id。跨窗口的趋势报告与面向读者的更新说明，由时序分析线基于这些逐窗产物生成。

## 十、配置体系

系统的配置分散在几个文件中，各司其职。理解它们的分工和读取机制，是调参和运维的基础。

### 配置文件一览

| 文件 | 管什么 | 敏感吗 |
|------|--------|--------|
| `codes/settings.yaml` | LLM 调用、ΔG 强度、各链路截断/抽样、图谱边计算与合成等全部可调参数 | 否（但不含密钥） |
| `classify/taxonomy_base.json` | tasks/skills/jobs 三体系标签源文件路径 | 否 |
| `codes/api-key.txt` | DeepSeek API key | 是（已 gitignored） |
| `codes/jd_fetch/config.yaml` | 远端 job51 库 MySQL 连接 + 表清单 | 是（含密码） |
| `codes/jd_fetch/config_origin.yaml` | 本地 51job 库 MySQL 连接 + 表清单 | 是（含密码） |
| 各模块 `config.py` | 薄读取层 + 模块私有路径常量 | 否 |

读取机制的核心设计是：各模块的 `config.py` 按文件路径直接读 `settings.yaml`（用 PyYAML 解析），而不是通过 `import config` 跨模块传递。这天然免疫 Python 跨模块 `sys.modules` 缓存顺序问题——原来新闻参数必须模块内自洽的限制由此解除。`settings.yaml` 缺失或损坏时，各变量回退代码内置的同值默认，系统仍能运行。强度权重和合成参数还会写入快照的 `meta.json`，保证已建截面的解释不受日后参数改动影响。

### 体系基准开关：taxonomy_base.json

`classify/taxonomy_base.json` 是切换三体系标签源的唯一开关。文件内容很简单——三个键值对，指定 tasks/skills/jobs 各自读 `classify/` 下的哪个 JSON 文件。改这一个文件即全局切换，builder/extractor/graph 全部跟随，无需改代码。当前三基准均已切至最新版：任务 v0.3（`Tasks/tasks.json`，27 项）、技能 v0.5（`Skills/skills0821.json`，49 项）、岗位 v2.0（`Jobs/jobs_v2.json`，131 个）。

如果只想临时做 A/B 对比实验，可以用环境变量 `TAXONOMY_BASE_TASKS`、`TAXONOMY_BASE_SKILLS`、`TAXONOMY_BASE_JOBS` 覆盖单项——仅当次运行生效，不改文件。正式切换走文件修改（=新纪元，旧窗口自包含不回填）。

需要注意：切回旧体系前先确认映射判据已校准——2026-08-16 曾有教训，技能基准从文献版切到 Builder 版后，映射漏判了语义等价条目（"大语言模型幻觉防控"与"AI 幻觉校验与质量控制"被判为不同技能），原因是基准与映射判据共同决定映射质量。

### 敏感凭证

敏感凭证不放在 `settings.yaml` 中，而是各自独立管理。

DeepSeek API key 存在 `codes/api-key.txt`（已 gitignored）。文件格式为 `(provider) label: sk-xxx`，程序用正则 `sk-[A-Za-z0-9]+` 提取。`load_api_key()` 的读取优先级是：文件 > 环境变量 `DEEPSEEK_API_KEY` > 环境变量 `ANTHROPIC_AUTH_TOKEN`。

JD 数据库凭证在 `codes/jd_fetch/` 下两个 YAML 文件中：`config.yaml` 指向远端 job51 库（2025-2026 批），`config_origin.yaml` 指向本地 51job 库（JD-Origin 早期批）。两者都含 MySQL 连接参数（ip/port/username/password/db_name）和表清单。仓库转公开前需处理这些密码。

### CLI 与配置的关系

大部分 CLI 脚本接受与 `settings.yaml` 参数同名的命令行参数，用于临时覆盖当次运行的值。覆盖规则因参数而异——多数参数 CLI 不传时读 config 默认值，传了就用 CLI 值。以薪资加权为例：`run_base_build.py` 不传 `--no-salary-weight` 时读 `graph_base.salary_weight`（当前 false），传了 `--no-salary-weight` 则强制关闭（与 config 无关）。也就是说，CLI 是覆盖手段而非唯一来源，配置文件才是默认的真实来源。
